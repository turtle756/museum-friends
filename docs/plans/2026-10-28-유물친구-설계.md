# 유물 친구 찾기 · 설계 (2026-10-28 승인)

## 1. 무엇을 만드나
- **대상**: 아이(6~9세 가정)와 함께 온 가족. 폰은 부모가 든다.
- **문제(가정, 현장 확인 필요)**: 부모는 유물을 설명해 주고 싶어도 아는 게 없어 지나치고, 아이는 금방 지루해한다.
- **흐름**: 질문 카드를 부모가 읽음 → 아이가 유물을 찾음 → QR이나 번호로 확인 → 아이가 실물을 보고 관찰 질문에 답 → 맞히면 유물 친구 등장 → 아이의 상상 대답이 친구의 첫 대사 → 도감 완성.
- **원칙**: 화면은 질문, 정답은 실물. 친구는 관찰로만 생긴다. 아이 대답은 그 폰에만 저장한다.
- **첫 대상 박물관(선호)**: 부천활박물관. 콘텐츠 파일만 바꾸면 다른 박물관에도 쓴다.

## 2. 기술 결정
| 항목 | 결정 | 이유 |
|---|---|---|
| 서버 | Flask, Vercel에 배포 | 팀이 아는 기술, 11~14주 실습(API 계약·pytest·DATABASE_URL·health)과 맞물림. Vercel은 Flask를 설정 없이 지원하고 깨어나는 데 몇 초 이내 |
| DB | Neon Postgres | 5분 쉬면 잠들지만 다음 요청에 바로 깸. Supabase 무료는 7일 쉬면 직접 풀어야 함. 둘 다 Postgres라 바꾸려면 `DATABASE_URL`만 교체 |
| 정적 파일 | `public/` (Vercel CDN) | Vercel은 Flask static 폴더를 무시함. 로컬 Flask도 같은 폴더를 같은 주소로 제공 |
| 콘텐츠 | `content/tour.yaml` (Git) | 팀원이 GitHub 웹에서 고치고 PR로 남김. 자동 검사가 배포 전에 오류를 막음 |
| 아이 기록 | 브라우저 localStorage | 서버에 개인정보가 가지 않음 |

검토했지만 버린 것
- Render 무료: 15분 쉬면 깨우는 데 약 1분, 저장 파일이 재시작마다 사라짐.
- 정적 웹앱 + Supabase 직접: 보안을 접근 규칙(RLS)으로만 지켜야 하고 Flask를 안 씀.
- PythonAnywhere 무료: 외부 DB 접속이 막혀 Neon/Supabase를 못 씀.

Vercel 무료(Hobby)의 제약: **계정 주인 한 명만 배포할 수 있다.** 팀원은 PR을 올리고, 배포 담당(서버 담당)이 main에 합쳐 배포한다.

## 3. 구조
```
휴대폰 브라우저
 ├─ public/ (HTML·CSS·JS·그림)  ← Vercel CDN, 바로 열림
 ├─ GET  /api/tour    ← Flask, CDN이 5분 캐시
 └─ POST /api/events  ← Flask → Neon (이름 없는 횟수만)
아이 진행·대답 → 그 폰의 localStorage
```
- 입구에서 `/api/tour`를 한 번 받아 폰에 보관한다. 전시실 통신이 끊겨도 끝까지 진행된다.
- 서버나 DB가 죽어도 관람 흐름은 돈다. 통계만 빠진다.

## 4. 화면 6개
1. **시작**: 투어 제목, 친구 수·시간·나이, 시작/이어 하기. 콘텐츠 불러오기 실패 시 다시 시도.
2. **질문 카드**: 부모가 읽을 찾기 질문, 접힌 힌트, "찾았어요".
3. **찾기 확인**: 화면 안 QR 카메라 또는 번호 세 자리 입력. 다른 유물·없는 번호 안내.
4. **관찰 질문**: 아이가 누를 큰 버튼. 틀리면 "다시 자세히 볼까?"만, 감점 없음.
5. **친구 등장**: 그림 위 눈·입, 짧은 이야기, 상상 질문 → 대사(조사 자동 처리).
6. **도감**: 모은 친구, 이미지로 저장, 처음부터, 기록 지우기.

QR 내용은 `https://주소/?a=101`. 휴대폰 기본 카메라로 찍어도, 화면 안 카메라로 찍어도 같은 번호로 처리한다.

## 5. API 계약
| method·path | 요청 | 성공 | 오류 |
|---|---|---|---|
| `GET /api/tour` | 없음 | 200, 투어 JSON (`checked_by`·`note` 제외) | 없음 |
| `POST /api/events` | `{tour, visit(uuid4), type, code}` | 204 저장, 202 DB 꺼짐 | 400 형식 오류, 413 너무 큼, 503 DB 오류 |
| `GET /health` | 없음 | 200 `{status, db: ok/off}` | 503 `{db: error}` |

이벤트 `type`: `start`, `found`, `wrong_code`, `observe_retry`, `observe_ok`, `complete`. 유물 관련 4종은 `code`가 투어에 있는 번호여야 하고, `start`·`complete`는 `code`가 없어야 한다.

## 6. 콘텐츠 규칙 (`content/tour.yaml`)
- 투어: `id`, `title`, `museum`, `status`(예시/확정), `age`, `minutes`, `cards`(1~12장).
- 카드: `code`(따옴표 친 세 자리), `name`, `find`, `hint`, `observe{question, choices 2~4개, answer}`, `story`, `imagine{question, line, skip_line}`, `image`(public/ 아래), `image_alt`, `face{x, y, size}`, `source`, `image_credit`, `checked_by`, `note`(선택).
- `line`에는 `{답}`이 꼭 있고, 조사는 `{을/를}` `{이/가}` `{은/는}` `{과/와}` `{아/야}` `{으로/로}`만 쓴다.
- `status: 확정`이면 모든 카드에 `source`·`image_credit`·`checked_by`가 있어야 한다.

## 7. 오류 대비
- 카메라 없음·거부·카카오톡 등 앱 안 브라우저 → 번호 입력으로 진행.
- 통신 끊김 → 보관한 콘텐츠로 계속. 처음부터 못 받으면 "다시 시도".
- 콘텐츠 오류 → 자동 검사(CI)가 PR 단계에서 막음. 서버는 잘못된 콘텐츠로 시작하지 않음.
- 이벤트 전송 실패 → 무시(관람 흐름에 영향 없음).

## 8. 개인정보
- 받지 않는 것: 이름, 사진, 연락처, 아이의 대답.
- 서버에 가는 것: 무작위 방문 번호(uuid), 이벤트 종류, 유물 번호, 시각.
- 폰에 남는 것: 진행 상황과 아이의 대답. 도감의 "기록 지우기"로 즉시 삭제.

## 9. 테스트
- 자동(pytest): 콘텐츠 검사, API 계약(정상·경계·오류), health, 통계 명령.
- 자동(node --test): 조사 처리, 진행 저장 로직.
- 수동: 11주 친구 3~5명 5분 과제 관찰, 12~13주 지인 가족 현장 테스트(동의), 13주 키보드·200% 확대·색 대비.

## 10. 범위
- **Must(11주)**: 화면 6개, 번호 입력, 진행 저장, 예시 카드 3장, 배포.
- **Should(12~13주)**: 실제 유물 콘텐츠·사진(출처·허락), QR 인쇄물, 통계 보기, 현장 테스트 반영.
- **Could**: 나이대 3단계, 오프라인 캐시(서비스 워커).
- **Won't(이번 학기)**: 관리자 화면, AI 대화, 회원가입.

## 11. 역할 (3명)
- 서버 담당: 개발 전체, 배포, DB.
- 팀원 A: 현장 관찰·사용자 테스트 기록(docs/research).
- 팀원 B: 콘텐츠 작성(질문·이야기·출처), 사진 정리, 발표 자료.
- 콘텐츠 수정은 `docs/content-guide.md`를 따라 GitHub 웹에서 PR로 한다.
